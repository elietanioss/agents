## 1. Structure: monolith vs. modular monolith vs. microservices

**Default posture the agent should hold going in:** start modular-monolith. Splitting a service out is a two-way door (extraction is mechanical if the module was cleanly bounded); merging two live independently-deployed services back together is a one-way-door-shaped mess in practice (data has diverged, on-call habits have formed, contracts are externally visible) even though nothing about a service boundary is architecturally sacred. Asymmetric reversal cost is reason enough to default to the cheaper starting point (`fundamentals.md` §7).

**Source:** Martin Fowler, *"MonolithFirst,"* martinfowler.com/bliki, 3 June 2015 `[T]`: "you shouldn't start a new project with microservices, even if you're sure your application will be big enough to make it worthwhile" — because establishing correct service boundaries requires domain knowledge the team doesn't yet have, and a monolith is far cheaper to re-carve while that knowledge is still forming. Fowler separately coined the **"microservices premium"** (martinfowler.com/microservices) `[T]`: microservices add a fixed tax — service discovery, distributed transactions, inter-service testing, operational multiplication (§6 of `fundamentals.md`'s CAP/PACELC territory) — that only pays off once system complexity clears a threshold high enough to be worth it.

**RULE 1.1** — IF the team has fewer than ~2 pizza-team's worth of engineers *per proposed service boundary* (rule of thumb, not a law) THEN default to modular monolith; a service per 1–2 engineers guarantees more inter-service coordination overhead than the split saves. **UNLESS** the services have genuinely independent compliance, scaling, or failure-domain requirements that make shared deployment itself the risk (e.g., a component handling regulated PII vs. one that doesn't). `[UNVERIFIED]` for the specific team-size ratio; `[T]` for the direction, derived from Conway's Law (`fundamentals.md` §3, RULE 3.2) — you cannot run N independently-owned services with fewer than N independently-accountable owners without the "independence" becoming fictional.

**RULE 1.2** — IF module boundaries inside the current monolith are not yet stable — i.e., RULE 4.2 co-change coupling from `fundamentals.md` (two modules changing together in a majority of commits) still fires across what would become the proposed service split THEN do not extract; extraction bakes an unstable boundary behind a network call, converting a cheap in-process refactor into an expensive cross-service migration. **RATIONALE:** this is `fundamentals.md` §4's empirical-coupling test applied as a *gate* on distribution, not just a diagnostic.

**RULE 1.3 (the actual trigger to extract a service)** — IF a specific module has (a) a distinct scaling profile (needs to scale independently of the rest by a wide margin — e.g., 50x request volume vs. the rest of the system), OR (b) a distinct deployment cadence forced by an external party (e.g., a vendor SDK requiring frequent hotfixes that would otherwise force full-system redeploys), OR (c) a distinct failure-isolation requirement (its crashing must not take down the rest) THEN extraction is justified — pick the *smallest* boundary that resolves the specific forcing function, not the most "logical" domain boundary. **UNLESS** the forcing function can be resolved more cheaply in-process (e.g., a bulkhead/circuit-breaker pattern, or vertical scaling per RULE 8.1) — check the cheaper fix first, because the network hop is never free (§6, RULE 6.1).

**RULE 1.4** — IF the pitch for microservices is organizational ("we want independent team deploys," "teams keep blocking each other") rather than technical (scaling, isolation) THEN this is a Conway's-Law-driven decision (`fundamentals.md` §3, RULE 3.2, reverse Conway maneuver) — solve it by reshaping team ownership and deployment pipelines first (e.g., modular monolith with per-module CI gates and codeowners) and only reach for network-level separation if pipeline-level separation genuinely can't deliver independent deploys (e.g., a single process binary that can't be partially deployed). **RATIONALE:** many "we need microservices" requests are actually "we need independent deployability," which modular monoliths with strict module boundaries and separate CI stages can deliver without a network hop.

**Cross-reference:** the failure mode of extracting along the wrong boundary is `anti-patterns.md` §"distributed monolith" — services that are separately deployed but still share a database or release train, inheriting network cost with none of the isolation benefit.

## 2. Communication: sync request/response vs. async/event-driven vs. batch; queues; backpressure

**RULE 2.1** — IF the caller needs the result to proceed (the next line of caller logic depends on the response value) THEN use synchronous request/response. IF the caller only needs to know the request was *accepted*, not its eventual outcome THEN use async/event-driven. **UNLESS** the "eventual outcome" is itself needed later in the same user-facing interaction, in which case you need a way to surface it back (polling, webhook, websocket push) — don't choose async and then silently drop the requirement to close the loop.

**RULE 2.2** — IF two components are coupled synchronously and the callee's availability is lower than the caller needs, OR the callee's latency varies more than the caller's latency budget allows THEN insert a queue between them (turning a synchronous coupling into an async one) — this trades immediate consistency for availability, matching PACELC's L-vs-C axis (`fundamentals.md` §6) even inside a single system with no network partition in sight. **RATIONALE:** a queue converts a *temporal* coupling (both sides must be up at the same instant) into a *durable* one (the message waits) — this is the primary mechanical reason queues improve availability, not a vague "decoupling" claim.

**RULE 2.3 (when NOT to add a queue)** — IF the operation must confirm success before the caller proceeds (e.g., "was the payment authorized") THEN a queue does not remove the synchronous dependency — it just relocates where the caller blocks (either on the queue-consumer's ack or on a follow-up poll), and now you've added a second failure mode (the queue itself) without removing the first. **UNLESS** the design deliberately accepts "accepted for processing" as the response contract (e.g., order placed, fulfillment async) — that's a valid product decision, but it must be a stated product decision, not an accidental side effect of introducing a queue for other reasons.

**RULE 2.4 (backpressure)** — IF a producer can emit work faster than a consumer can drain it, sustained, not just in bursts THEN the system needs an explicit backpressure mechanism (bounded queue + reject/shed, rate limiting, or slowing the producer) — an unbounded queue is not a fix, it is deferred and amplified failure (OOM or unbounded latency growth at the point the queue is finally drained). **Source:** the Reactive Manifesto v2.0 (Jonas Bonér, Dave Farley, Roland Kuhn, Martin Thompson, reactivemanifesto.org, 16 September 2014) `[T]` names backpressure explicitly as required for the "Elastic" and "Resilient" properties of a message-driven system: systems must "control the rate of message flow rather than let producers overload consumers." **Quantify the check with Little's Law** (John D. C. Little, *"A Proof for the Queuing Formula: L = λW,"* Operations Research 9(3), 1961, pp. 383–387) `[T]`: average items in the system L = arrival rate λ × average time-in-system W. IF λ (arrival rate) is rising and W (processing time) is constant or rising THEN L (queue depth, and therefore memory and latency) grows without bound — this is a formula, not a heuristic, and it is the concrete test for "will this queue blow up" before it does in production.

**RULE 2.5** — IF the workload is not time-sensitive within the business process (end-of-day reconciliation, monthly billing runs, bulk re-indexing) THEN batch, not streaming or per-event processing — batch amortizes per-operation overhead (connection setup, transaction commit) across many records and is simpler to reason about, retry, and audit than an equivalent stream pipeline. **UNLESS** the batch window itself becomes the bottleneck (the batch no longer fits in its allotted window as volume grows) — that's the concrete, measurable trigger to move to streaming, not "streaming is more modern."

**RULE 2.6 (fallacies check)** — Before treating any inter-component call as "just a function call architecturally," check it against Peter Deutsch's **Fallacies of Distributed Computing** (drafted 1994; eighth fallacy added by James Gosling, 1997; canonical list via Sun Microsystems / L. Peter Deutsch) `[T]`: the network is reliable; latency is zero; bandwidth is infinite; the network is secure; topology doesn't change; there is one administrator; transport cost is zero; the network is homogeneous. IF a design's error handling, timeout strategy, or retry policy implicitly assumes any of these THEN the design is wrong, not merely incomplete — every one of these is false in production at scale, and this list is the fastest audit for "did we just call a remote thing like it was local."

## 3. Data: SQL vs. NoSQL vs. event-store vs. search vs. cache; single-writer vs. multi; cache/CDN and invalidation; consistency vs. availability

**RULE 3.1** — IF the data has relationships that must be queried flexibly and not all access patterns are known upfront, AND the data has strong invariants that must hold across multiple records (e.g., double-entry accounting, inventory counts) THEN default to a relational (SQL) store — ACID transactions and joins are the tools built for exactly this, and every workaround (application-level joins, manually coordinated multi-document writes) reinvents them worse. **UNLESS** the invariant genuinely only ever touches a single entity's own document (in which case a document store's single-document atomicity is sufficient).

**RULE 3.2** — IF access patterns are few, known in advance, and dominated by key-based lookup or a small number of fixed query shapes, AND horizontal write scale beyond a single node is a real, present requirement (not anticipated) THEN a NoSQL store (document, wide-column, key-value) is justified — you are trading query flexibility and, usually, transactional strength for horizontal scalability and schema flexibility that a single relational primary cannot give you. **RATIONALE:** the decision is about matching the store's design center to the access pattern, not "NoSQL is more scalable" as a blanket claim — a correctly sized relational database (see RULE 8.1, vertical-first) outperforms most systems' actual load for years.

**RULE 3.3** — IF the domain's core requirement is "how did we get to this state" (audit, compliance, undo/replay, temporal queries, dispute resolution) rather than just "what is the current state" THEN consider an event-store / event-sourcing model — the append-only log is the source of truth and current state is a derived projection. **UNLESS** the team cannot yet answer "what do we do when we need to change how a past event is interpreted" (schema evolution of stored events) — that operational question must have an answer before adopting event sourcing, not after the log has years of old-shaped events in it. `[UNVERIFIED]` — widely practiced, but the specific operational maturity bar is a practitioner judgment, not a cited study.

**RULE 3.4** — IF a query need is "find records matching fuzzy, ranked, full-text, or faceted criteria" THEN add a dedicated search index (e.g., inverted-index engine) fed from the system of record — do not attempt to serve this need from the primary transactional store's `LIKE`/regex facilities past prototype scale; the primary store's indexing strategy is optimized for transactional access, not relevance ranking. Treat the search index as a read-only, rebuildable projection, never the system of record — if it can't be safely deleted and rebuilt from source data, something is architecturally wrong.

**RULE 3.5 (cache — when to add one, and the cost that's actually being paid)** — IF a specific read path is both (a) measured as a latency or load bottleneck (not assumed — see `verification.md` for how to establish this) and (b) tolerant of some staleness window THEN add a cache in front of it. **The rule that's usually skipped:** adding a cache is not free — it is *trading a data-freshness problem for a cache-invalidation problem*, and Phil Karlton's observation ("there are only two hard things in Computer Science: cache invalidation and naming things" — widely attributed, exact original citation undocumented) `[UNVERIFIED]` is operationally true often enough to be the default assumption. Before adding a cache, name explicitly: the invalidation trigger (TTL, event-driven bust, write-through), the staleness window the business can tolerate (a number, per `fundamentals.md` RULE 6.2), and what happens on a cache-stampede (all keys expiring simultaneously under load).

**RULE 3.6 (CDN specifically)** — IF content is read-heavy, changes infrequently relative to read volume, and read latency is dominated by geographic distance to origin THEN put a CDN in front of it. **UNLESS** the content is per-user/personalized at the response level (not just per-user at the request-auth level) — personalized-at-render content defeats CDN caching's core assumption (shared cache value across many requesters) and needs edge-compute or client-side personalization instead of naive full-response caching.

**RULE 3.7 (single-writer vs. multi-writer)** — IF two or more independent processes can write to the same record without a coordinating protocol THEN you have a conflict-resolution problem whether or not you've designed one — silence on this is not the absence of the problem, it's an undefined "last write wins by accident of timing." Default to single-writer per record (one owning service/process is the only writer; everyone else reads or requests a write through it) — this sidesteps the entire class of distributed write-conflict problems at the cost of that owner becoming a bottleneck/single point of failure for writes to that record. **UNLESS** the domain can tolerate a defined conflict-resolution strategy (CRDTs, vector clocks, application-level merge, last-write-wins with a documented and accepted loss condition) — multi-writer is viable, but only when the resolution strategy is a named, tested design decision, not a default.

**RULE 3.8 (consistency vs. availability, operationalized)** — Building on `fundamentals.md` §6 (CAP/PACELC): IF the business impact of showing slightly stale data is low (a view count, a "last seen" timestamp, a recommendation list) THEN choose availability/low-latency (AP-leaning, or PACELC's "EL" — favor latency) — don't pay a consistency tax for data nobody will act on incorrectly. IF the business impact of two conflicting writes both succeeding is high (double-spend, double-booking, overselling inventory) THEN choose consistency (CP-leaning, or PACELC's "EC" — favor consistency), accepting reduced availability during a partition or contention. **RATIONALE:** this is `fundamentals.md` RULE 6.3's reminder applied positively — CAP/PACELC only fires when the system is actually distributed; once it is, the choice must be made per data type, not once for the whole system (a single system commonly needs both postures for different tables/aggregates).

## 4. State: stateless vs. stateful; where state lives; idempotency

**RULE 4.1** — IF a compute unit (service instance, function, worker) can be killed and replaced without losing information the business cares about THEN keep it stateless — push all durable state to a store designed for it (database, cache, object store, queue). Stateless units are trivially horizontally scalable and trivially replaceable on failure; every unit of in-process state is a unit of special-case failure handling ("what do we do when this instance dies with unflushed state") that stateless design avoids entirely.

**RULE 4.2** — IF state must live in-process for performance reasons (e.g., an in-memory model, a hot cache, a game server's live session) THEN explicitly define: (a) the durability contract (is loss on crash acceptable, and to whom), (b) the recovery path (rehydrate from where, how long does it take), and (c) the ownership (which single instance is authoritative for this piece of state, tying back to RULE 3.7's single-writer rule). **UNLESS** the in-process state is fully reconstructible from durable storage cheaply (a rebuildable cache), in which case it's not "state" in the risk sense — it's a performance optimization with a defined miss path.

**RULE 4.3 (idempotency)** — IF an operation can be retried (by a client timeout-and-retry, a message queue's at-least-once delivery, or a user double-click) THEN the operation must be idempotent, or retries will duplicate side effects (double charges, duplicate orders, duplicate emails). **Source:** Stripe's public API design for idempotent requests (docs.stripe.com/api/idempotent_requests; Stripe Engineering, *"Designing robust and predictable APIs with idempotency,"* stripe.com/blog/idempotency) `[T]` for the pattern, `[TS]` for the specific mechanism details — establishes the now-industry-standard pattern: client generates a unique idempotency key per logical operation; server persists the (key → result) mapping; a retried request with the same key returns the original result without re-executing side effects, including replaying the original error if the first attempt failed. **RULE 4.3a** — this requires a durable store for the key→result mapping with its own retention/expiry policy (Stripe: 24 hours) — idempotency is not free; it trades a small amount of storage and a lookup for eliminating an entire class of duplicate-side-effect bugs, which is a near-always-good trade for any mutating operation reachable over an unreliable network (see RULE 2.6, fallacy #1: the network is not reliable).

**RULE 4.4** — IF at-least-once delivery is used anywhere in the system (most real queues and message brokers default to this, because exactly-once delivery across a network is not achievable without a coordinating protocol that itself needs idempotency to implement) THEN idempotency at the consumer is not optional — it's the only thing standing between "at-least-once" and "duplicated." Do not attempt to solve this by chasing exactly-once delivery semantics at the transport layer; solve it at the consumer with RULE 4.3's pattern, which is cheaper and actually achievable.

## 5. Build vs. buy vs. open-source vs. adopt-a-platform

**RULE 5.1** — Classify the capability on an evolution axis before deciding. **Source:** Simon Wardley, Wardley Mapping (originated at Fotango, c. 2005; canonical writeup: Simon Wardley, *"An introduction to Wardley (Value Chain) Mapping,"* blog.gardeviance.org, and Wardley, *Wardley Maps*, self-published/OSS, 2016) `[T]` for the evolution-stage taxonomy, `[UNVERIFIED]` for mapping any specific real-world capability onto a stage (that placement is a judgment call, not a formula). Four stages: **Genesis** (novel, uncertain, actively being invented) → **Custom-built** (understood but still bespoke per user) → **Product/rental** (repeatable, several vendors, feature-competing) → **Commodity/utility** (standardized, interchangeable, often metered).

**RULE 5.2** — IF the capability sits at Product or Commodity on the evolution axis THEN buy/adopt — you cannot out-invest a vendor whose entire business is that one capability, and building it yourself is pure opportunity cost with no differentiation to show for it (e.g., don't build your own object storage, email delivery, or payments processing). IF the capability sits at Genesis or Custom-built THEN building may be justified — **UNLESS** no part of your competitive differentiation depends on it, in which case even a Genesis-stage capability should probably be bought/rented/outsourced from someone whose differentiation *is* that capability, accepting rougher edges in exchange for not diverting your own scarce novel-work capacity onto someone else's problem.

**RULE 5.3 (the disqualifying question for "build")** — IF the capability is not part of what makes your product win against alternatives (not a source of competitive advantage) THEN default away from building regardless of evolution stage — engineering time spent on non-differentiating capability is engineering time not spent on the thing users actually chose you for. **RATIONALE:** this is the practical operationalization of Wardley's core argument — map effort to where it creates advantage, not to where it's merely possible.

**RULE 5.4 (open-source specifically)** — IF adopting an open-source component THEN evaluate it as "buy" for build-effort purposes but budget the *ongoing* cost separately: patching cadence, CVE monitoring, the bus-factor of the maintaining community (a single-maintainer project is a supply-chain risk regardless of license), and the fork/maintain-yourself cost if the project is abandoned. **UNLESS** the team has already validated the project's health (commit recency, maintainer count, issue-response latency, corporate/foundation backing) — "it's free and it's on GitHub" is not evaluation.

**RULE 5.5 (adopt-a-platform / PaaS / vendor lock-in tradeoff)** — IF time-to-market is the dominant constraint (a genuine one-way-door forcing function — e.g., a funding runway or a contractual launch date) THEN adopting a higher-level platform (PaaS, managed runtime, vertical SaaS) is justified even at the cost of some lock-in — you are explicitly trading reversibility for speed, so make that trade **consciously and record it as a `fundamentals.md` §7 one-way-door decision**, not by accident. **UNLESS** the lock-in cost is specifically the thing that's a one-way door with a broad blast radius (e.g., a proprietary data format with no export path) — in that narrow case, insist on an exit path (data export guarantees, an abstraction seam) before adopting, even under time pressure, because reversal cost here compounds instead of staying flat.

**Disqualifiers table (fires regardless of the above):**

| Disqualifier for "build" | Disqualifier for "buy/adopt" |
|---|---|
| Capability is available at Product/Commodity stage and isn't a differentiator (RULE 5.2/5.3) | Vendor's data-export/exit path doesn't exist or is contractually restricted (conflicts with `fundamentals.md` RULE 7.2's true one-way-doors) |
| Team lacks the specific expertise and the capability is not worth acquiring that expertise for | Compliance/data-residency requirement the vendor cannot contractually meet |
| Total cost of ownership (including the ongoing cost in RULE 5.4) exceeds vendor pricing over the realistic system lifetime | Vendor's roadmap/pricing model has a known cliff (e.g., aggressive usage-based pricing at the scale you're headed toward) |

## 6. Distribution: when NOT to distribute; the cost of a network hop

**RULE 6.1 (the hop is never free — quantify before adding one)** — Every network hop added to a request path introduces, at minimum: non-zero latency (RULE 2.6, fallacy #2), a new independent failure mode (that service can be down when the caller is up), a serialization/deserialization cost, and a new authentication/authorization boundary to secure. IF a proposed design adds a hop THEN it must state what capability that hop buys (independent scaling, independent deployment, failure isolation, technology-fit) that offsets these four fixed costs — "it's cleaner" or "it's more scalable" without naming which of these forcing functions applies is not sufficient justification (ties to §1 RULE 1.3).

**RULE 6.2 (the distributed-monolith trap)** — IF services are deployed independently but (a) share a single database or schema, or (b) must be deployed together/in a specific order to avoid breaking, or (c) share a release train/version lockstep THEN the system is a distributed monolith — it has paid the full cost of distribution (network hops, operational multiplication, partial-failure handling) while getting none of the benefit (independent deployability, independent scaling, failure isolation). **Source (naming/origin):** the pattern was named and discussed publicly by Ben Christensen (then at Netflix) at the Microservices Practitioner Summit, 2016, describing "coupling of distributed systems with binary/release dependencies" as an emerging common anti-pattern `[T]` for the phenomenon; `[UNVERIFIED]` for the exact attribution as the coinage's first use, since the pattern was independently observed and named by multiple practitioners in the same period. **The fix is not more distribution** — it's fixing the coupling (separate the shared database along the same boundary as the service split, or don't split yet — see §1 RULE 1.2). Full detail and additional smells: `anti-patterns.md` §"distributed monolith."

**RULE 6.3 (when NOT to distribute — the default-negative test)** — IF none of RULE 1.3's three forcing functions (independent scaling need, independent deploy cadence forced externally, failure isolation requirement) currently apply, and are not concretely on the roadmap with a committed timeline THEN do not distribute — "we might need to scale this independently later" is not a forcing function, it's a speculation, and per `fundamentals.md` RULE 7.1/7.2, a service-boundary decision made today for a maybe-future need should be evaluated as if it were a one-way door being taken pre-emptively, which is nearly always the wrong side of the reversibility trade (you're paying the irreversible cost now for an uncertain future benefit). Prefer keeping the module boundary clean *inside* the monolith (RULE 5.3 of `fundamentals.md`'s information-hiding test) so extraction remains cheap *when and if* the real forcing function materializes.

## 7. Where to put complexity: edge vs. core; smart endpoints vs. orchestration

**RULE 7.1** — IF a piece of logic is specific to one consumer's needs (a particular client's data-shaping, a particular channel's protocol translation) THEN push it to the edge (that consumer's own adapter/BFF — Backend-for-Frontend — or the endpoint itself) rather than building conditional branches for it into the shared core. **RATIONALE:** this is `fundamentals.md` §5's information-hiding rule applied to placement — the core shouldn't need to change when one consumer's needs change; hiding consumer-specific variation at the edge keeps the core's design decisions stable.

**RULE 7.2 (smart endpoints and dumb pipes)** — IF choosing where inter-service integration logic should live (routing rules, transformation, business-rule branching) THEN default to putting it in the endpoints (the services themselves), keeping the communication substrate (message broker, service mesh, ESB) as simple as possible — a "dumb pipe" that only moves bytes reliably. **Source:** James Lewis & Martin Fowler, *"Microservices,"* martinfowler.com/articles, 25 March 2014 `[T]` — cites Unix pipes and the early web as the model: components that "receive a request, apply logic as appropriate and produce a response," integrated over simple protocols (HTTP/REST, lightweight messaging), explicitly contrasted with the "Enterprise Service Bus" model where significant business/routing logic lived in the integration layer itself. **RULE 7.2a (the failure mode this prevents)** — IF business logic accumulates inside the message broker/ESB/API-gateway configuration (transformation rules, conditional routing based on payload content, orchestration workflows) THEN that logic becomes untested-by-normal-means, unowned by any single team, and a single point of coupling for every service that flows through it — the same god-service smell from `fundamentals.md` RULE 4.1, just relocated into infrastructure instead of a service.

**RULE 7.3 (orchestration vs. choreography — when centralizing IS correct)** — IF a business process has more than a handful of steps with complex conditional branching, needs a single place to see/debug/resume the overall process state, or has compliance requirements around process auditability (must prove step N happened before step N+1) THEN centralize as explicit orchestration (a workflow engine or an orchestrator service) rather than choreography (each service reacting to the previous one's event with no central process view). **UNLESS** the process is simple and linear enough that choreography's benefit (no single component knows/depends on the whole flow, so any step can evolve independently) outweighs the debuggability cost of a process with no single owner. **RATIONALE:** this is a direct case of RULE 6.1's fundamentals — orchestration re-centralizes coupling deliberately, in exchange for observability and auditability; choreography avoids that coupling at the cost of "what actually happened" becoming reconstructable only by correlating logs across N services. Neither is universally correct; the trigger is process complexity and audit requirements, not fashion.

## 8. Concurrency and scaling: vertical-first; scale-out triggers

**RULE 8.1 (vertical-first)** — IF current load is within roughly one order of magnitude of what a single larger/well-tuned instance of the current store/service can handle THEN scale vertically (bigger instance, better indexes, connection pooling, query optimization) before scaling out (sharding, read replicas, service splitting). **RATIONALE:** vertical scaling preserves single-writer simplicity (RULE 3.7), avoids distributed-transaction and cross-node-consistency problems entirely, and is nearly always a two-way door (resize down again is trivial) whereas scale-out topology changes (sharding key choice, partitioning scheme) are frequently one-way doors per `fundamentals.md` RULE 7.1 — a bad shard key is expensive to change once data has accumulated under it. `[UNVERIFIED]` for the specific "one order of magnitude" threshold — treat as a starting heuristic, validate against actual instance-size ceilings for the store/runtime in question, which change yearly (see `sources-and-currency.md`).

**RULE 8.2 (the concrete trigger to scale out)** — IF vertical scaling has hit a hard ceiling (largest available instance/SKU is already in use and still insufficient), OR the data volume itself exceeds what fits well on one node regardless of instance size, OR a regulatory/data-residency requirement forces partitioning by geography THEN scale out — and choose the partition/shard key from the dominant access pattern (the key most queries already filter or group by), not from convenience (e.g., not an auto-increment ID) — repartitioning later is precisely the one-way-door cost RULE 8.1 is trying to defer.

**RULE 8.3 (concurrency within a single node — measure before adding threads/async)** — IF a workload is I/O-bound (waiting on network/disk more than computing) THEN concurrency (async I/O, more connections/workers) improves throughput cheaply. IF a workload is CPU-bound THEN adding concurrency beyond the available core count adds scheduling overhead without adding throughput — the fix is more cores (vertical, RULE 8.1), algorithmic improvement, or horizontal scale-out (RULE 8.2), not more threads on the same cores. **RATIONALE:** this is Little's Law again (§2, RULE 2.4) applied to compute instead of queues — throughput is bounded by service capacity, and concurrency only helps the portion of W (time-in-system) that was spent waiting, not the portion spent computing.

**RULE 8.4 (scale-out's hidden tax)** — IF scale-out is adopted THEN RULE 3.7 (single-writer) and RULE 4.3/4.4 (idempotency) become mandatory, not optional — every benefit of horizontal scale-out is paid for with exactly the distributed-write and at-least-once-delivery problems those rules exist to solve. Do not evaluate "should we scale out" independently from "have we solved single-writer and idempotency" — a team that hasn't is not ready to scale out safely regardless of load numbers.

- §3's data rules and §4's state rules supply the vocabulary (single-writer, idempotency, consistency-per-data-type) that `domain-matrix.md` specializes per system class — e.g., what "consistency vs. availability" means concretely for an embedded/RTOS system differs from a web SaaS, but both start from RULE 3.8 here.
- §5's build-vs-buy disqualifiers feed directly into `stack-selection.md`, which is the applied version of this section for specific technology choices (framework, database engine, cloud provider).
- §7's orchestration-vs-choreography and edge-vs-core placement rules are the decision layer beneath the *process* recommendations in `methodologies.md` (e.g., which methodology assumes which placement).
- Every `[UNVERIFIED]` threshold in this file is a candidate for calibration against a real system's telemetry and history — `verification.md` describes the procedure (fitness functions, ATAM-style scenario testing, mining commit history per `fundamentals.md` RULE 4.2) for turning a heuristic number into a validated one for a specific system, and `sources-and-currency.md` sets the refresh cadence for the ones tied to infrastructure capability (instance sizes, managed-service ceilings) that change yearly regardless of the rule's logic staying sound.
